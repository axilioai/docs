AXI-1982 telemetry compatibility baseline

Match the cost-map schema to the wire and let supported SDKs survive a future telemetry frame kind.

Implementation in review · staging evidence pending · 2026-09-01 · AXI-1982

One-line summary
Keep retention-expired cost maps as raw null, normalize them to {} in Python’s high-level API, and add one forward-compatible Python frame fallback; prove the deployed seam with one narrow staging smoke.

Executive summary

Decision. Fix two concrete compatibility failures without redesigning telemetry frames. The backend will describe both required cost maps as nullable because retention-expired responses already return null. Python will expose that raw value as None and preserve its high-level dictionary contract by returning {}. Python will also preserve a frame with a new non-empty string kind as UnknownFrame instead of rejecting the whole page. Go already preserves unknown discriminants and needs only native regression coverage.

This is the baseline that permits a later backend frame kind to ship before its typed SDK model. It does not make old strict SDK releases tolerant retroactively. A future producer must wait until this baseline is released and the team accepts its adoption risk.

Why documentation alone is insufficient
Customers cannot “work with” a response that the generated client rejects before returning it. Documentation can explain raw null and unknown kinds, but it cannot change Pydantic validation or recover known frames from a rejected page.

Customer trigger: retention has expired

{
  "frames": [],
  "total": 0,
  "limit": 100,
  "offset": 0,
  "retention_expired": true,
  "sdk_call_costs": null,
  "inference_costs": null
}

A customer requests an older session through Python. The backend correctly withholds expired telemetry, but the generated model rejects both null maps. The customer receives a parsing exception instead of an empty trace with retention_expired=True.

Customer trigger: the backend adds a frame kind

{
  "frames": [
    {"kind": "span", "span_id": "call-1", "...": "..."},
    {"kind": "metric", "name": "cpu.utilization", "value": 0.72},
    {"kind": "log", "body": "finished", "...": "..."}
  ]
}

Without the baseline, Python rejects the complete page because metric is not a recognized discriminator. The customer loses access to the valid span and log as well. With the baseline, those known siblings remain typed and the metric remains available as raw unknown data until a later SDK adds MetricFrame.

Compatibility promise. After the tolerant SDK baseline is released, a new non-empty string frame kind may precede its typed SDK model. This promise applies to supported baseline-or-newer Axilio SDKs, not every historical client or arbitrary OpenAPI generator.

Implementation

Backend and OpenAPI

  • Mark SDKCallCosts and InferenceCosts as nullable at the Huma response struct, while keeping both properties required.
  • Keep the existing retention wire value null. Do not add a second normalization rule in the handler.
  • Pin the generated OpenAPI shape and both normal and retention-expired JSON bodies in router tests.
  • Bump the API contract version with the schema change.

Python SDK

  • Regenerate required nullable maps so the raw model accepts and exposes None.
  • Coalesce each page’s missing cost map with {} inside SessionTelemetry.trace().
  • Patch only the generated response union with an explicit unknown-kind model. The patch is exact, idempotent, regeneration-safe, and rejects known discriminator values.
  • Keep normal generated Log and Span constructors and validation intact.
  • Cover raw nullability, high-level normalization, mixed known/unknown pages, malformed known frames, and patch drift under Pydantic 1 and 2.
  • Record the compatibility change in the Python release notes.

Go SDK

  • Keep the generated tolerant-reader implementation unchanged.
  • Use native endpoint and high-level telemetry tests to pin null-map and unknown-kind behavior.
  • Do not add a standalone compatibility executable or a second validation framework.

Deployment smoke

Keep one backend-owned, manually dispatched workflow. It runs only from reviewed main, allows only dev or staging, and refuses production. It installs exact candidate SDK refs before credentials exist, converges only dedicated E2E fixtures, mints one key for the run, performs the live assertions, writes redacted evidence, revokes the key in unconditional cleanup, and fails if revocation cannot be confirmed.

The smoke proves the deployed OpenAPI, normal wire response, retention-expired wire response, and installed Python behavior. Future-kind and malformed-known behavior stay in deterministic native SDK tests because the deployed backend does not emit a third kind yet.

Pros of the chosen approach

  • Fixes the customer-visible parsing error while keeping the raw wire contract honest.
  • Prevents one future frame from making all known frames on a page unusable.
  • Keeps validation strict for malformed known frames.
  • Uses each repository’s native tests and leaves only deployed behavior to the live smoke.

Costs we accept

  • Raw Python callers must handle None for the two cost maps.
  • Python owns a small fail-closed post-generation exception until its generator supports an open union directly.
  • Unknown frames are preserved but not typed, so callers must inspect kind and raw fields.
  • Older strict SDKs can still fail on a future kind. Release and adoption sequencing remains a product decision.
  • The smoke requires a dedicated fixture and short-lived staging credential, which adds limited operational surface.

Release sequence

  1. Review native changes. Complete focused backend, Python, and Go review and CI. Keep the Python and docs PRs in draft while staging evidence is pending; Go may merge because this PR does not change its package version or runtime behavior.
  2. Deploy the backend schema fix. Merge the backend normally and let the reviewed deployment workflow promote that revision to staging. No third frame kind ships in this step.
  3. Run the staging smoke. Test the deployed backend with the exact Python candidate under both supported Pydantic majors. Preserve the redacted result and confirm key revocation.
  4. Release the tolerant baseline. Publish Python 0.20.0 only after the smoke passes. Go can merge independently because its runtime behavior does not change.
  5. Publish customer documentation. Merge docs only after the backend contract and Python package they describe are available.
  6. Gate a future frame kind. Before emitting metric or another kind, explicitly accept the remaining risk from customers on older SDKs. The backend may then ship before the SDK version that adds a typed model.

Out of scope

  • Returning {} instead of null on the raw retention-expired wire.
  • Adding metric, its producer/storage path, or a typed MetricFrame.
  • Guaranteeing future-kind compatibility for SDK releases older than this baseline.
  • Server-side capability negotiation, version headers, frame filtering, or feature flags.
  • Redesigning live versus archived frame schemas, pagination, retention, storage, or billing joins.
  • Creating standalone SDK probes, a general evidence framework, or production monitoring in this ticket.
