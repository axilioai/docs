Telemetry can include console output, operation attributes, and captured SDK
inputs or results. Decide whether to enable it as part of your session's data
handling policy.

## Enable or disable Telemetry

Telemetry is enabled by default. Set `telemetry: false` on a direct allocation,
or `telemetry_enabled: false` on an agent or an ad hoc run, when you do not
want Axilio to create a live or retained Telemetry record for the resulting
session. A run's [stream](/agents/monitor#stream-a-run) still carries the
run's own events and the model's text live, and keeps none of it.

```json
{
  "telemetry": false
}
```

This setting is all-or-nothing:

- no frames are available from the live Telemetry stream;
- **Timeline** and **Console** have no Telemetry to display; and
- no retained frame archive is available after the session.

<Warning>
  There is no live-only Telemetry mode. Copy that says Telemetry remains
  available live when storage is disabled is outdated.
</Warning>

Recording is a separate control, and it is off by default. Leaving recording
off does not disable Telemetry, and `telemetry: false` does not disable a
recording.

| Configuration | Telemetry | Recording |
| --- | --- | --- |
| Defaults | Live and retained | Not captured |
| `recording: true` | Live and retained | Captured |
| `telemetry: false` | Not created | Not captured |
| `recording: true` and `telemetry: false` | Not created | Captured |

## Understand the access window

How long you can read a session's Telemetry depends on your
[organization plan](/billing/overview#organization-plans) when the session
started. These are the standard windows:

<div id="axilio-plan-retention" />

If you change plans later, sessions that already exist keep their window.
Daily, Weekly, and Monthly dedicated rentals don't change it either. An
Enterprise contract can set a different window, and the contract's window is
the one that applies.

The retention clock begins when the session is created, not when it ends or
when the last frame arrives. Read `retention_expired` from a retained
[frames response](/telemetry/retrieve) before interpreting an empty archive.

Once the window closes, the frames response returns no frames and sets
`retention_expired` to `true`. A daily cleanup job then deletes the stored
Telemetry. Deletion happens on a later run of that job, not at the instant
access ends.

<Note>
  The access period is not a guaranteed minimum. Access enforcement and
  physical cleanup are separate lifecycle operations.
</Note>

If Axilio cannot establish that the session remains inside its access window,
the retention check fails safe and withholds the trace.

An explicit organization policy can disable Telemetry writing. Other
configurations can leave a session with no positive access window. Customer
access can then expire immediately even when frames may have been emitted. Do
not infer the session's physical storage history from an empty or expired
response.

## Keep session history after agent deletion

Deleting an agent does not delete the sessions its runs created.
Session details and retained Telemetry remain addressable by `session_id`,
subject to the normal retention policy.

You can no longer mint a live Telemetry URL after the session ends. Existing
history remains a session resource rather than a child of the deleted
agent.

## Know what Telemetry can contain

Raw frames can contain producer attributes and data supplied by your SDK
calls. SDK-call spans use these attributes:

| Attribute | Content |
| --- | --- |
| `axilio.sdk.input` | The captured input parameters. |
| `axilio.sdk.output` | The captured result. |

Each nonempty input and output value is capped independently at 4,096 bytes.
A truncation marker indicates when the value exceeded the cap. Truncation is a
size control, not a privacy control.

Current capture behavior is:

- `Keyboard.typeText` input replaces its `text` value with
  `<redacted:string:N>`, where `N` is the character count;
- malformed typed-text input is replaced with a placeholder;
- other nonempty SDK inputs and all nonempty SDK results can be captured
  verbatim;
- empty bytes, `{}`, and `null` are omitted; and
- transport operations such as `Protocol.handshake` and `Device.info` do not
  create SDK-call spans.

<Warning>
  Redaction is not schema-driven. A typed request does not imply that its
  sensitive fields are removed.
</Warning>

There is no separate switch for SDK-call input/output capture. To prevent
these values from entering the Telemetry record, disable Telemetry for the
session. Otherwise, avoid putting secrets or unnecessary sensitive data in
SDK parameters, return values, or custom attributes.

The Dashboard details pane renders a curated set of fields. A value can exist
in a [raw frame](/telemetry/frames) without appearing in **Timeline** details.

## Protect Telemetry access

Retained frames and the event stream accept your customer API key and
require organization viewer access. A session outside your organization is
reported the same way as a missing session.

A live `telemetry_url` is a session-scoped bearer secret:

- do not write it to application logs;
- do not include it in screenshots, analytics, or support bundles;
- keep it out of browser history and referrer data;
- do not share it as a device-control or recording credential; and
- discard it when you no longer need it.

The URL is read-only, scoped to one session, and expires about an hour after
it is issued. Read the session again for a fresh one. See
[Live telemetry](/telemetry/live).

## Data-handling checklist

1. Decide whether the session needs Telemetry and recording independently.
2. Keep sensitive values out of SDK inputs, outputs, and custom attributes.
3. Treat the live URL and API key as secrets.
4. Use raw frames when you need attributes that the Dashboard does not show.
5. Check `retention_expired` instead of treating every empty archive alike.
6. Base deletion commitments on your approved data policy, not the customer
   access-expiration timestamp.
